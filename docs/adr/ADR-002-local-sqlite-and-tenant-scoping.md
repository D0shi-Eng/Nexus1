# ADR-002: SQLite محلي مع TenantScope إلزامي

**الحالة:** مقبول  
**التاريخ:** 16 أغسطس 2026

## السياق

يتطلب المنتج Local-first مع SQLite محلياً، وفي الوقت نفسه يجب أن يمنع التصميم منذ البداية تسرب البيانات بين المستأجرين عند الانتقال إلى وضع مشترك أو متزامن. لا تسمح بيانات التطبيق أن تكون جداول JSON عامة دون قيود أو إصدارات أو علاقات صريحة.

## القرار

تستخدم نسخة سطح المكتب SQLite كمخزن معاملات محلي عبر مستودعات Rust فقط. كل مورد أعمال يحتفظ بـ`tenant_id` غير فارغ؛ كل حالة استخدام تنشئ `TenantScope` من جلسة المستخدم؛ وكل استعلام وتعديل يمرر `tenant_id` كشرط لازم في طبقة المستودع. تُعرّف مفاتيح وفهارس مركبة عند الحاجة مثل `(tenant_id, id)` وقيود فريدة ضمن المستأجر. تُحفظ المهاجرات مرقمة وتختبر قابليتها لإعادة التنفيذ الآمن.

## البدائل التي روجعت

| البديل | القرار | السبب |
|---|---|---|
| وضع `tenant_id` في الواجهة فقط | مرفوض | قابل للتجاوز ولا يمنع تسرب الاستعلامات في الطبقات الخلفية. |
| جدول عام JSON لكل الموارد | مرفوض | يضعف النزاهة والفهرسة والمهاجرات وتدقيق الحقول الحرجة. |
| PostgreSQL محلياً منذ البداية | مرفوض | عبء تركيب وتشغيل لا يتناسب مع تطبيق محلي أولاً. |
| SQLite مع مستودعات مقيدة بالنطاق | مقبول | بسيط في التشغيل ويؤسس انضباط العزل وقابلية الانتقال لخادم PostgreSQL. |

## العواقب

لا تتصل واجهة React بقاعدة البيانات ولا تحمل بيان اتصال. توجد طبقة مبدل/مستودع تضمن الإيجار وتستطيع لاحقاً دعم محول PostgreSQL. لا يعني وجود `tenant_id` أن قاعدة SQLite واحدة متعددة العملاء في الإنتاج آمنة تلقائياً؛ سيخضع وضع الخادم المستقبلي لتصميم صفوف وسياسات قاعدة بيانات منفصل.

## معايير القبول

يجب أن تفشل اختبارات القراءة والتعديل التي تستخدم معرف مستأجر مختلفاً، وأن تتضمن كل عملية تدقيق معرف المستأجر، وألا يوجد استعلام تجاري في المستودعات دون مرشح `tenant_id`.
